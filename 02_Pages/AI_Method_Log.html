The AI Method Log

Required with every project deliverable — this one is about the work, not the writing

 

What this is, in one paragraph

The AI Review Log covers what you asked AI about your writing. The AI Method Log covers what you asked it about the work itself — the analysis, the data, the code, the plan. Same honesty, different question.

Five fields. The one that matters most is how you verified it.

Why this exists, and why it is separate

The Review Log asks you what you rejected. That is the right question about prose: a critique of your argument is either persuasive or it is not, and declining it is an act of judgment.

It is the wrong question about technical work. Nobody is critiquing your buffer distance. The failure mode here is different and worse: you run a workflow you cannot justify. The tool proposes a projection, a join predicate, a resampling method, a statistic, a line of Python — it sounds right, it executes without error, and the result is wrong in a way nothing will tell you about.

The rule this log enforces

You may not adopt a method you cannot defend independently of the tool that suggested it. Not “the AI said so”. Not “it ran”. You checked it against something, and you can say what.

The five fields

The five required fields of the AI Method Log
Where AI entered the workWhich stage of the technical work you own — data discovery, CRS or schema decisions, tool and parameter selection, scripting or automation, debugging, quality checks, cartographic choices, documentation. For project managers: scheduling, dependency and integration analysis, risk identification, or status synthesis.
What you asked, and with what contextThe actual prompt, and the context you supplied with it — the data, the coordinate reference system, the constraint, the failure message. A model told nothing about your data will answer about someone else's.
What it proposedThe method, parameter, tool, or code it gave you.
How you VERIFIED itWhat you checked it against: the software documentation, a known-good result, a hand calculation, a test that would have failed if the suggestion were wrong. “It looked right” is not verification.
What it got wrongAnything it proposed that turned out to be incorrect, and the evidence that showed it. Confidently wrong is the normal failure mode here.

What counts as verification

Any of these. All of them take minutes.

  • The documentation. Esri, GDAL, the standard, the published specification. If the tool named a geoprocessing parameter, the parameter is documented.
  • A known-good result. Run it on data where you already know the answer. A spatial join you can count by hand on ten features tells you whether the predicate is the one you meant.
  • A hand calculation. One feature, one number, done manually. Area, distance, a proportion. If they disagree, something is wrong and you have found it early.
  • A test that would fail. Deliberately feed it the case that should break — a null geometry, a feature crossing the antimeridian, a raster with a different cell size. If nothing breaks, either you are safe or your test is not testing.
  • A second, independent route to the same answer. Different tool, different method, same question. Agreement is evidence; disagreement is a finding.

What does not count

“It looked right.” “It ran without errors.” “I asked it again and it said the same thing.” Asking the same model twice is not a second opinion. It is the same opinion, delivered twice, and it will agree with itself while being wrong.

Where AI actually helps in GIS work

This is not an exhaustive list and you are not required to use all of it. It is here so that “I did not know what to use it for” is not an available answer.

Stages of technical work where AI is worth using, and what to watch for

Data discoveryWhich agencies publish this, at what resolution, under what license; what the equivalent dataset is called in another countryInvents plausible dataset names and dead URLs. Every source it names must be opened before it is cited.

Scripting and automationDraft an arcpy or Python script for a repetitive step; explain someone else's script line by lineUses deprecated methods confidently. It ran is not it is correct.

Two worked lines, so the standard is clear

Weak — scores 1

Where: Reprojection.
Asked: “What projection should I use for Nigeria?”
Proposed: Web Mercator.
Verified: Looked correct in the map view.
Wrong: Nothing noted.

No context supplied, no verification, and the answer is wrong for anything involving area.

Strong — scores 4

Where: Reprojection, before computing settlement area by state.
Asked: “I have polygons across Nigeria, roughly 4°N–14°N, and I need area in km² per state. Which equal-area projection, and what does it cost me?”
Proposed: An Albers equal-area conic with standard parallels chosen for the extent.
Verified: Computed the area of Lagos State in the proposed projection and compared it with the published figure — agreed to under 1%. Repeated in Web Mercator to see the size of the error: 60% high.
Wrong: Its first answer was Web Mercator, and it only offered an equal-area projection after I said the output was area. It optimises for what you asked, not for what you are doing.

Analyst or project manager — both, differently

If you own an analysis component, this log is about the analysis. If you are the Project Manager, it is about the work you own: the plan, the schedule, the dependency and integration analysis, the risk register, the status synthesis. The requirement is the same — use it on the real work, and show how you checked what it told you. “My role is not technical” is not an exemption.
