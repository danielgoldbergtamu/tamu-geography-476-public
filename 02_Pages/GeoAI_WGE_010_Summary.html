What does not exist

  • Municipio-level CUMULATIVE counts. The second attempt at the report failed three ways: no query is issued on a plain load, the page button does not respond to a synthetic click, and Power BI had cached the previous session's expansions - so the expand-to-force-a-query technique works once per state per browser profile.
  • Any municipio-scale case list for a border state. Both states that could be reconstructed are interior, which is the limit that survives.
  • Municipio boundary geometry. INEGI publishes it; this project holds centroids only, which is why exposure is a production figure rather than a herd count inside a polygon.

What was NOT built, and why

Read this section first if you read nothing else. The deliverable that was refused is the one you would most likely have produced.

  • Nayarit and Yucatan, which were most of the captured rows. Harvested 122 of 141 and 91 of 118. The matrix stopped mid-state and nothing recovers the remainder.
  • Pooling the two reconciled states into one test. The selection is at state level, so a pooled comparison would cross exactly the line the design exists to respect.

What no check would have caught

The rules and gates this course runs on, and why each one would have passed the version that was wrong.

  • any checker here - a partially harvested state is a plausible number attached to a real place, and nothing in this repository knows what the number should have been except the register it is now checked against
  • the analysis itself - the test would have run happily on the wrong attribution and returned a confident answer

What went wrong while building it

  • The first parser attributed municipios by row order and produced Yucatan 276 against a published 118. Assuming the capture was in state-then-municipio order. It is in the order the matrix was scrolled and expanded. Caught by Reconciling each state's municipios against a count captured from a different source. Without that check the number would have shipped..
  • The second parser, attributing purely by name, then lost Zacatecas - 180 of 191 - because Guadalupe, Benito Juarez and Villa Hidalgo are municipios in several of the captured states. One rule where the data needed two. Caught by The same reconciliation, which is why it runs on every parse..

What to take from it

  • Reconcile a scraped total against a figure captured from somewhere else before using it. The check that caught a 158-case error cost four lines.
  • Selection bias has a level. The Power BI matrix selected STATES on the response variable, not municipios, so a strictly within-state comparison is legitimate on data that is unusable across states.
  • Drop a partially harvested unit rather than carrying it at the wrong total. An incomplete state is worse than a missing one because it still looks like data.
  • Report the smallest effect a test could have seen. In Zacatecas the test could resolve 1.8 km and found 0.4, which is a much stronger statement than any p-value.
  • Test the assumption your null model rests on. Every null here is weighted by cattle on the premise that cases follow cattle; at municipio scale that premise holds at rho 0.27 and 0.11 - true, and weak.
  • When new evidence closes a limitation you published, go back and edit the limitation. A caveat that is no longer true understates the result and is a quiet form of hedging.
  • "No change" is a result of a review. Four of the five earlier logs are listed with the reason the new data cannot touch them.

What this means for the job you are about to apply for

The instructor asked whether new data let anything be updated. The valuable answer was mostly no, with one exception stated precisely, and a correction to a caveat the previous log had written about itself. Knowing which of your own conclusions a new dataset can and cannot reach is the skill; reaching for all of them because the data is new is how a reanalysis becomes a press release.
